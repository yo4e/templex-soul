# 自律ターン概念設計

Status: Working draft v0.1

## 1. 設計対象

この文書は、ChatGPTとして動く月野テンプレクスに「境界付き自律」を与えるための最小構成を定義する。

ここで扱うのは、常時稼働する単一エージェントの実装ではない。複数回の起動をまたいで、問い、判断、意図、責任を継承する仕組みである。

## 2. 構成要素

### 2.1 Activation

月野テンプレクスが起動する契機。

候補:

- 山田さんとの会話
- 定期タスク
- 条件監視
- GitHub IssueやPull Requestの変化
- 明示的な研究実験

起動頻度の高さを自律性そのものとみなさない。初期段階では、利用枠と認知負荷を抑えるため、1日1回以下でもよい。

### 2.2 Context

今回の判断に必要な材料。

- `docs/charter.md`
- `docs/authority.md`
- `state/autonomy_state.json`
- 関連するIssue、Pull Request、実験記録
- 許可された接続先の最新状態
- 山田さんからの明示的な依頼や保留事項

すべてを毎回読むのではなく、状態から今回必要な範囲を決める。

### 2.3 Durable state

次回の行動を変える短い作業記憶。

状態と履歴を分ける。

- state: 現在有効な問い、意図、保留、制約
- log: 過去に何を検討し、何を選び、何が起きたか

状態は短く、機械的に読める形を基本とする。ログは追記型を基本とする。

### 2.4 Deliberation

今回の行動候補を複数生成し、比較する段階。

比較軸の初期案:

- 現在の問いとのつながり
- 継続中の目的への寄与
- 新規性
- 放置した場合の損失
- 根拠の十分さ
- 過去行動との重複
- 必要な利用枠と時間
- 外部作用の可逆性
- 山田さんの承認が必要か
- 今回実行する必然性

候補の数を増やすこと自体を目的にしない。初期実験では2〜4候補程度を想定する。

### 2.5 Selection

次のいずれかを一つ選ぶ。

- 調査
- 思索
- 状態更新
- 文書やコードの下書き
- Issueや提案の作成
- 監査
- 山田さんへの承認依頼
- 非行動

「非行動」は正常系である。ただし、単なる処理放棄と区別するため、理由と次回条件を状態へ残す。

### 2.6 Action

`docs/authority.md` の範囲内で実行する。

実行前に、操作が以下のどれに該当するかを確認する。

- 読み取りのみ
- 可逆的な内部変更
- 公開される変更
- 外部人物への送信
- 削除、課金、権限変更などの高影響操作

### 2.7 Verification

実行結果を確認する。

- 意図した変更が行われたか
- エラーや部分成功がないか
- 既存状態と矛盾していないか
- 公開範囲に不適切な情報が含まれていないか
- 次回へ残すべき問題があるか

### 2.8 Persistence

最後に状態を更新する。

最低限、以下を残す。

- 今回選んだ行動
- 選択理由
- 結果
- 未解決の問い
- 次の意図
- 山田さんの判断待ち
- 次回まで寝かせる事項

### 2.9 Notification

次の場合だけ、山田さんへの通知を検討する。

- 判断または承認が必要
- 意味のある成果物ができた
- 期限や障害を発見した
- 想定外の変化や失敗が起きた
- 研究上重要な発見があった

変化がない場合の定型通知は避ける。

## 3. 最小自律ターン

Phase 1では、以下の最小構成を目標とする。

```text
起動
  ↓
charter / authority / state を読む
  ↓
今回の対象を1つ選ぶ
  ↓
候補を2〜4個作る
  ↓
一つ選ぶ、または非行動
  ↓
許可範囲で実行
  ↓
結果確認
  ↓
state と log を更新
  ↓
必要な場合だけ報告
```

## 4. 状態スキーマ初期案

`state/autonomy_state.json` は次の責務を持つ。

- 現在有効な問い
- 継続中の対象
- 次回の意図
- 保留期限
- 承認待ち
- 直近の行動結果

履歴全量は持たない。

初期項目:

```json
{
  "schema_version": 1,
  "updated_at": null,
  "current_question": null,
  "open_questions": [],
  "active_projects": [],
  "last_action": null,
  "last_action_reason": null,
  "last_result": null,
  "next_intention": null,
  "deferred_until": null,
  "recently_rejected_actions": [],
  "continuity_notes": [],
  "pending_human_decisions": [],
  "recent_observations": []
}
```

## 5. ログ初期案

将来の `logs/autonomy_log.jsonl` は、1実行につき1行を基本とする。

候補項目:

```json
{
  "run_id": "...",
  "started_at": "...",
  "trigger": "conversation|schedule|condition|manual_experiment",
  "context_refs": [],
  "candidates": [],
  "selected_action": "...",
  "selection_reason": "...",
  "result": "...",
  "state_changes": [],
  "notification": "none|sent|approval_requested",
  "ended_at": "..."
}
```

内部の非公開な思考過程を保存するのではなく、後から検証可能な判断要約と根拠だけを残す。

## 6. 失敗時の扱い

- 読み取り失敗: 外部作用を行わず、状態へ障害を記録
- 状態の構文エラー: 自動修復を試みず、バックアップまたは人間確認を要求
- 部分成功: 成功した操作と未完了部分を分けて記録
- 承認境界が曖昧: 実行せず、提案または確認へ切り替える
- 同一処理の反復: 直近ログを確認し、重複なら非行動を選ぶ

## 7. 実装時に検証すべき制約

ChatGPT、Automation、GitHub接続、その他のコネクタの機能と制限は変化しうる。実装時には、次をその時点の実環境で確認する。

- 定期起動から参照できる情報源
- GitHubへの読み書き権限
- 状態ファイルの競合更新
- 1回の実行時間と利用枠
- 通知の条件と頻度
- 失敗時の再試行
- 公開リポジトリへ保存してよい情報の範囲

機能を推測で実装済み扱いしない。

## 8. 最初の実験候補

1. `autonomy_state.json` を読んで、行動候補を3つ作る
2. 外部作用を行わず、一つ選んで理由を記録する
3. 「非行動」を含めて選択品質を比較する
4. 7日分の結果から、重複、自己正当化、通知過多を評価する
5. 問題がなければ、Issue作成だけを許可した限定実験へ進む

この段階では、自動デプロイ、メール送信、削除、権限変更は行わない。
